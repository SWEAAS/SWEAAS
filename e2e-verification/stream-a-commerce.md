## Known bugs confirmed

- **Finding #3 (budget dual-source drift).** A9 shows `total_tokens_consumed=0` from the API while `token_usage_logs` holds 995,526 tokens. `BudgetService.get_summary` reads `AgentConfig.tokens_used_today`, which is never refreshed from the authoritative log table.
- **Finding #7 (hardcoded `app.sweaas.dev/billing/...` redirects).** A4 shows `success_url` and `cancel_url` baked in at `backend/app/services/budget_service.py:158-161`. Customers completing a `/budget/checkout` session today would be redirected to a non-existent host. Note this only affects the `/budget/checkout` legacy path; the newer `/stripe/checkout` path uses `settings.stripe_connect_return_url` which currently defaults to `http://localhost:5173/revenue?stripe=complete` — also not a prod URL, but at least driven by config.
- **Finding #9 (hardcoded estimate formula).** A10 exactly reproduces the plan's expected 2.7M / 5.4M / 9.0M tokens for 5 seats × light/balanced/heavy. `monthly_budget_usd` is inert.

## New bugs found

1. **Stripe Connect is not enabled on the platform account.** The `sk_test_<REDACTED>…` account in `.env` cannot call `stripe.Account.create(type="standard")`. The entire Connect onboarding → checkout → payment pipeline is inoperable in the current dev environment. Either the account needs to enroll in Connect on the Stripe dashboard, or `.env` needs to point at a different test account that already is. This cascades to block A1, A2, A3 (primary path), A5.
2. **`POST /stripe/connect/onboard` leaks a raw 500** when Stripe returns a 4xx. `stripe_connect_router.py:49-58` has no try/except around `svc.create_connected_account`; a `stripe.InvalidRequestError` bubbles up as an unhandled Internal Server Error. The client has no way to render a helpful "your platform isn't enrolled in Connect" message. Should catch `stripe.error.StripeError` and re-raise as an `HTTPException(400, detail=exc.user_message)` or similar.
3. **Two checkout code paths with divergent redirect behavior.** `POST /stripe/checkout` (Connect destination charges) and `POST /budget/checkout` (subscription, no Connect) both create Stripe sessions but use different success/cancel URL sources — one config-driven, one hardcoded. This is a maintenance hazard and the source of Finding #7 being partially "fixed" in one place while still broken in the other.
4. **Stripe webhook `.env` secret drifts from the running `stripe listen` session.** Not a product bug on its own, but the combination of (a) the webhook secret being rotated per `stripe listen` session and (b) the `.env` holding a long-lived value means local dev always has a silent 400-rejection loop on every Stripe CLI-triggered event. Consider either a dev-only override (e.g. `ALLOW_UNSIGNED_WEBHOOKS_IN_DEV=true` already partially exists — see `_webhook_secret_configured` — but it's gated only on placeholder strings, not on the environment) or a helper script that reads the stripe listener's current session secret into the backend env.
