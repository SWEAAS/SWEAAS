I am building a SWE as a service platform. In this document I describe my vision for the platfrom and your task will be to bring it to life together with me. So the vision is SWE as a service. Many people, with and without startups, have brilliant ideas these days and usually can easily bring it to life with a little vibe coding. However the problem comes when they actually have to scale the service efficiently and cost-effectively. Enter SWEAAS (SWE As A Service). The vision is that anyone will have access to a ready-to-go SWE team to run their company, thus saving costs of hiring developers, entire SWE teams, and having to hand out a lot of their equity. This oth saves money and allows solo founders to be very productive and scale very fast.

So now to talk about the platform, I will start by describing my vision for the backend
BACKEND:
When a user/organisation onboards onto the platform through the onboarding process, we create a github repository on our organisational github for them (just like replit does), and we take their email optionally to give them access to the repo so they can be able to directly edit the code if needed. The effect is that we will have all the code of the project on our github with a github app installed so that AI agents can be able to access and iterate on the code. Note that security is very important and users should never be able to see other users's data. S
Now comes the AI agents. The AI agents are the engineeers. We have devops, research, frontend, etc. engineers as described in the msitarzewski/agency-agents github repository. We will allow the AI agents to iterate on code, implement user feedback or owner feedback (stored in database) to improve the app, fix bugs (sentry), handle payment integrations (stripe), handle call center (some useful integration), etc. There will be multiple AI agents for various users so we must find a way to run all these agents efficiently and in a scalable sandboxed manner so that agents never mix user data, never cross interact with different user services, eetc. It is also important to make sure to fit the client budget so Ai agents wlll never exceed a user's budget. Hopefully, we will be able to use as many integrations as possible without necessarily having to build some functionalities from scratch, while still keeping costs manageable. We hope to bring all AI develpments to date together in a nice way that is still cost-effective.
An important construct to maintain in this project is hierarchy of ai agents. the hierarchy should resemble that of a typical SWE department of a big tech company, starting with the CTO, and then all the sub-hierarchies and subordinates. this is because we want expert AI agents that store memory and always know what they worked on in the past, what worked, what didn't work, etc. so ideally, every sub-system could have a engineering manager for example with context of the whole project but not so specialised. their work would be to orchestrate the specialised AI agents that each own say a folder or feature and are experts in that domain. Their memory, i assume, can be managed via RAG, or via MD files in the codebase. the codebase should be indexed, and integrated with RAG to allow good retrieval and context management. importantly, the CTO simply orchestrates as well. the code is only edited by specialised agents, while orchestrators give feedback up the hierarchy, this process should be deterministic, and very efficient to avoid context loss, high compute usage, etc. this will have to be ideated upon.
